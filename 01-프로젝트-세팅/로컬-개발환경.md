# 로컬 개발환경

## 목적 / 범위
로컬 개발환경(Local Dev Environment)의 구성 요소를 이해하고, 프로젝트 세팅 시 **무엇을/왜/어떻게** 결정해야 하는지 설명할 수 있도록 정리한다.

- 포함: OS/셸, 런타임, 패키지 매니저, 에디터/도구체인, 환경변수, Git, 디버깅/로그, 로컬 서버, 파일시스템, 권한/네트워크, 재현성
- 제외: 특정 회사/특정 레포의 실행 방법(개별 프로젝트 문서로 분리)

---

## 필수 도구
프로젝트 유형과 무관하게 "대부분의 프론트엔드 로컬 환경"에서 사실상 필수인 것들.

- **OS + Shell**
  - macOS/Linux: zsh/bash 등
  - Windows: PowerShell(또는 WSL 사용 여부는 선택)
- **Git**
  - 버전관리/협업/히스토리 추적
- **런타임**
  - Node.js(프론트엔드 툴체인의 사실상 표준 런타임)
- **패키지 매니저**
  - npm/yarn/pnpm 중 하나(의존성 설치/스크립트 실행)
- **에디터**
  - VSCode/WebStorm/Cursor 등 (코드 탐색/리팩토링/확장)

## 권장 도구(선택)
필수는 아니지만 "생산성/품질/재현성"을 올리는 도구들.

### 버전 고정/재현성
- **Node 버전 매니저**: nvm / volta / asdf 등
  - 이유: PC가 바뀌어도(또는 협업 시에도) 동일한 Node 버전 재현
- **패키지 매니저 고정**: pnpm / Yarn (택1)
  - 이유: 동일한 의존성 설치/해결 결과 재현(락파일 포함)
- **corepack**(필요 시)
  - 이유: pnpm/yarn “버전”을 프로젝트 기준으로 고정하는 데 도움

### 코드 품질/형식
- **Formatter/Linter**
  - prettier, eslint 등(프로젝트에 따라)
  - 목적: 코드 스타일 충돌 방지, 실수 감소

### 개발/디버깅 편의
- **브라우저 DevTools**
  - 네트워크/성능/메모리/스토리지 디버깅
- **터미널 유틸**
  - rg(검색), fd(파일찾기) 등 (선택)

### 컨테이너(선택): Docker
- 역할
  - 로컬에서 실행 환경을 표준화("내 PC에서는 되는데?" 문제를 줄임)
  - DB/캐시/메시지큐 같은 의존 서비스들을 쉽게 띄움
  - CI와 유사한 실행 환경 재현
- 언제 필요한가
  - 백엔드/DB/캐시 등 외부 의존성이 있는 프로젝트
  - 온보딩 시간을 줄여야 하는 팀/프로젝트
  - OS 차이로 설치가 자주 깨지는 의존성이 있는 경우
- 주의
  - 프론트만 단독 개발이면 오버헤드가 될 수 있음
  - 파일 마운트/성능 이슈(특히 macOS)로 DX가 나빠질 수 있음

### 오케스트레이션(선택): Kubernetes (kind/minikube/k3d)
- 역할
  - 배포 환경(K8s)과 동일한 구조를 로컬에서 검증
  - 서비스 간 네트워킹/디스커버리/인그레스 등 운영 관점 테스트
- 언제 필요한가
  - 로컬에서 "운영 환경에 가까운 통합 테스트"가 필요한 경우
  - 마이크로서비스/클러스터 리소스 설정을 확인해야 하는 경우
- 주의
  - 학습/운영 비용이 크므로 "필요할 때만"도입하는 것이 일반적

## 시작하기(클론/열기)
학습 관점에서 "로컬 개발환경을 세팅한다"는 아래 순서를 의미한다.

1) **런타임/패키지 매니저 준비**
- Node 설치(버전 정책 결정: 최신/LTS/프로젝트 고정)
- npm/yarn/pnpm 선택(락파일 전략과 연결)

2) **에디터/확장 세팅**
- TypeScript/ESLint/Prettier 등 "개발 경험"을 결정하는 도구 연결

3) **Git 기본 설정**
- user.name/email, line ending(특히 windows), 기본 브랜치, ssh/https 인증 등
  
> 핵심: 시작 단계에서 결정한 "버전 고정/도구체인/인증 방식"이 이후 유지보수 비용을 좌우한다.

## 로컬 검증 체크리스트
로컬 개발환경이 "잘 갖춰졌다"를 판단하는 기준.

### 재현성
- [ ] Node 버전이 고정되어 있다(도구/파일/정책 중 하나로)
- [ ] 패키지 매니저/락파일이 일관되다
- [ ] 새 PC에서도 같은 절차로 동일한 결과를 만들 수 있다(문서화 포함)
- [ ] (선택) Docker로 의존 서비스가 재현 가능하다(compose 등)
- [ ] (선택) 운영이 K8s라면 로컬에서도 최소 흐름이 검증 가능하다(kind/minikube/k3d)

### 개발 경험(DX)
- [ ] 에디터에서 TS/lint/Format 이 의도대로 동작한다
- [ ] 디버깅(브레이크포인트/소스맵/네트워크)이 가능하다
- [ ] 로그 확인/필터링 흐름이 정리되어 있다

### 보안/권한
- [ ] 비밀값은 코드/커밋에 들어가지 않는다(.env, .gitignore 등)
- [ ] 로컬 인증(ssh/https 토큰 등)이 안전하게 관리된다

## Troubleshooting
로컬에서 가장 자주 마주치는 문제를 “원인-확인-해결”로 정리한다.

### 1) Node 버전 차이로 빌드/설치가 깨짐
- 원인: 개발자마다 Node 버전이 달라 의존성/빌드 결과가 달라짐
- 확인: cmd 창에 `node -v`입력으로 각 로컬 환경의 node 버전 확인
	```bash
	nvm install
	nvm use
	node -v
	```
- 해결: nvm/volta/asdf 또는 `.nvmrc`/`engines`로 버전 고정
	```json
	{
		"engines": {
			"node": ">=20 <21"
		}
	}
	```
  
### 2) 의존성 설치는 되는데 실행 결과가 다름(락파일 불일치)
- 원인: 락파일이 없거나, 매니저가 섞여 설치됨
- 확인: 락파일 1종인지, 매니저가 통일됐는지
- 해결: 매니저 고정 + 락파일 유지 + 재설치

### 3) 환경변수 누락/오염
- 원인: `.env` 누락, 변수 이름 불일치, 쉘에 남은 값이 덮어씀
- 확인: 로드 위치/우선순위 점검
- 해결: `.env.example` 제공, 변수 스키마 문서화, 로드 순서 통일

### 4) Windows line ending/권한 이슈(선택)
- 원인: CRLF/LF 차이, 실행 권한/경로 정책
- 해결: git 설정/에디터 설정/WSL 사용 여부 결정
