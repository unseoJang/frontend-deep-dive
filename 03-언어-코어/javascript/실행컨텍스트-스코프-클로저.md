# 실행 컨텍스트 · 스코프 · 클로저

## 학습 목표

아래 흐름을 하나의 코드로 설명한다.

```text
함수 호출
→ 실행 컨텍스트 생성과 스택 push
→ 렉시컬 환경에서 식별자 탐색
→ 함수 종료와 스택 pop
→ 남아 있는 함수가 외부 환경을 참조하면 클로저로 상태 유지
```

이 문서는 이벤트 루프, `this`, 가비지 컬렉션의 세부 구현은 다루지 않는다.

## 먼저 답해보기

자료를 읽기 전에 각 질문에 1~3문장으로 답한다.

1. 실행 컨텍스트란 무엇이며 왜 필요한가?
2. 함수가 호출되고 끝날 때 스택은 어떻게 변하는가?
3. `inner()`는 왜 호출된 위치가 아니라 선언된 위치의 변수를 찾는가?
4. 외부 함수가 끝났는데 내부 함수는 왜 외부 변수에 접근할 수 있는가?

답이 틀려도 괜찮다. 읽은 뒤 같은 질문에 다시 답해 변화한 부분을 확인한다.

## 전체 그림

```js
const x = "global";

function outer() {
  const x = "outer";

  return function inner() {
    console.log(x);
  };
}

const fn = outer();
fn(); // "outer"
```

이 코드에는 세 개념이 모두 들어 있다.

- `outer()`와 `inner()`가 호출될 때 각각의 실행 컨텍스트가 스택에 쌓인다.
- `inner` 안의 `x`는 선언 위치를 기준으로 `inner → outer → global` 순서로 탐색한다.
- `outer()`가 끝나도 `inner`가 외부 환경을 참조하므로 `outer`의 `x`에 접근할 수 있다.

## 1. 실행 컨텍스트

### What

실행 컨텍스트(Execution Context)는 ECMAScript 구현이 **실행 중인 코드의 런타임 상태를 추적하기 위한 스펙상의 장치**다.

실행 컨텍스트는 JavaScript 코드에서 직접 접근하는 일반 객체가 아니다. 함수에만 존재하는 개념도 아니며 전역 코드와 모듈 코드를 평가할 때도 사용된다.

### Why

JavaScript 엔진은 코드 실행 중 다음을 알아야 한다.

- 지금 어떤 코드를 실행하고 있는가?
- 식별자 탐색은 어떤 환경에서 시작하는가?
- 현재 함수가 끝나면 어디로 돌아가는가?

실행 컨텍스트가 이 실행 상태의 기준을 제공한다.

### How

함수 호출 흐름을 학습 수준에서 단순화하면 다음과 같다.

```text
함수 호출
→ 실행 컨텍스트 생성
→ 실행 컨텍스트 스택에 push
→ 함수 본문 실행
→ 함수 종료
→ 스택에서 pop
→ 이전 실행 컨텍스트로 복귀
```

```js
function a() {
  b();
}

function b() {
  debugger;
}

a();
```

`b()`의 `debugger`에서 멈췄을 때 개념적인 스택은 다음과 같다.

```text
top → b 실행 컨텍스트
      a 실행 컨텍스트
      전역 실행 컨텍스트
```

`b()`가 끝나면 `b`가 먼저 pop되고 `a`로 돌아간다.

> 실행 컨텍스트는 명세 모델이고, DevTools의 Call Stack과 엔진의 스택 프레임은 구현·도구 관점이다. 학습할 때 대응시켜 볼 수 있지만 완전히 같은 개념이라고 단정하지 않는다.

## 2. 렉시컬 환경과 스코프

### What

스코프(Scope)는 식별자가 보이고 참조 가능한 범위다.

렉시컬 환경(Lexical Environment)은 식별자 바인딩을 기록하는 환경 레코드와 바깥 환경으로 이어지는 참조로 구성되는 스펙상의 모델이다. 실행 컨텍스트는 식별자 탐색을 시작할 렉시컬 환경을 가리킨다.

### Why

중첩된 코드에 같은 이름이 여러 번 선언될 수 있기 때문에, 엔진에는 어떤 바인딩을 선택할지 결정하는 규칙이 필요하다.

### How

JavaScript는 렉시컬 스코프를 사용한다. 함수가 **호출된 위치가 아니라 선언된 위치**를 기준으로 바깥 환경이 정해진다.

식별자를 만나면 현재 환경에서 찾고, 없으면 바깥 환경으로 이동한다. 끝까지 찾지 못하면 `ReferenceError`가 발생한다.

```js
const value = "global";

function outer() {
  const value = "outer";

  return function inner() {
    console.log(value);
  };
}

function run() {
  const value = "run";
  const inner = outer();
  inner();
}

run(); // "outer"
```

탐색 경로는 다음과 같다.

```text
inner 환경
→ outer 환경: value 발견
→ 탐색 종료
```

`inner()`가 `run()` 안에서 호출되어도 `run`의 `value`는 탐색 경로에 포함되지 않는다.

### 선언 종류와 스코프

- `var`: 함수 스코프
- `let`, `const`: 블록 스코프
- `let`, `const`의 바인딩은 만들어져도 초기화 전에는 TDZ에 있어 접근하면 `ReferenceError`가 발생한다.

```js
function check() {
  console.log(a); // undefined
  // console.log(b); // ReferenceError

  if (true) {
    var a = 1;
    let b = 2;
  }

  console.log(a); // 1
  // console.log(b); // ReferenceError
}
```

호이스팅은 코드가 실제로 위로 이동하는 현상이 아니다. **실행 전에 선언 종류에 따라 바인딩이 준비되고 초기화되는 시점이 다르다**고 설명하는 편이 정확하다.

## 3. 클로저

### What

클로저(Closure)는 함수와 그 함수가 생성될 때의 렉시컬 환경에 대한 참조의 결합이다.

특별한 문법으로 나중에 생성되는 것이 아니라 함수가 만들어질 때 형성되는 성질이다.

### Why

내부 함수가 외부 함수의 실행이 끝난 뒤에도 외부 바인딩을 읽거나 변경할 수 있는 이유를 설명한다. 상태 은닉, 콜백, 이벤트 핸들러 등에서 사용된다.

### How

```js
function createCounter() {
  let count = 0;

  return function increment() {
    count += 1;
    return count;
  };
}

const counter = createCounter();

console.log(counter()); // 1
console.log(counter()); // 2
```

`createCounter()`의 실행 컨텍스트는 함수 종료와 함께 스택에서 pop된다. 하지만 반환된 `increment` 함수가 `count`가 있는 외부 렉시컬 환경을 참조하므로 해당 바인딩에 계속 접근할 수 있다.

클로저가 저장하는 것을 단순히 “값의 복사본”이라고 보면 안 된다. 두 함수가 같은 바인딩을 참조하면 변경된 값을 함께 관찰할 수 있다.

```js
function createState() {
  let value = 0;

  return {
    increase() {
      value += 1;
    },
    read() {
      return value;
    },
  };
}

const state = createState();
state.increase();
console.log(state.read()); // 1
```

## 세 개념 연결하기

| 질문 | 설명 |
|---|---|
| 지금 무엇이 실행 중인가? | 실행 컨텍스트와 스택이 실행 상태와 복귀 순서를 관리한다. |
| 이 이름은 어디의 값인가? | 렉시컬 환경의 바깥 참조를 따라 식별자를 탐색한다. |
| 함수가 끝났는데 상태가 왜 남는가? | 남아 있는 함수가 외부 렉시컬 환경을 참조하는 클로저이기 때문이다. |

핵심 연결 문장은 다음과 같다.

> 실행 컨텍스트가 현재 실행 상태를 추적하고, 렉시컬 환경과 스코프 체인이 식별자 탐색 경로를 정하며, 클로저가 함수 생성 당시의 외부 환경 참조를 유지한다.

## 자주 하는 오해

1. **실행 컨텍스트는 함수 실행에 필요한 값을 모은 객체다.**
   - 일반 객체가 아니라 런타임 평가 상태를 추적하는 스펙상의 장치다.

2. **스코프는 함수를 호출한 위치에 따라 바뀐다.**
   - JavaScript의 스코프는 선언 위치로 결정되는 렉시컬 스코프다.

3. **클로저는 외부 값을 복사해 저장한다.**
   - 함수가 외부 환경의 바인딩을 참조한다고 이해하는 편이 정확하다.

4. **외부 함수의 실행 컨텍스트가 pop되면 모든 지역 변수도 즉시 사라진다.**
   - 실행 컨텍스트의 스택 제거와 렉시컬 환경의 생존 여부는 같은 문제가 아니다. 외부 참조가 남아 있으면 필요한 환경이 유지될 수 있다.

5. **실행 컨텍스트는 이벤트가 발생할 때만 생긴다.**
   - 이벤트가 없어도 전역·모듈·함수 코드를 평가할 때 필요하다.

## 직접 검증하기

1. 위 예제를 브라우저 DevTools의 Console에 붙여 넣는다.
2. `inner` 또는 `increment` 안에 `debugger`를 추가한다.
3. Call Stack에서 현재 호출 순서를 확인한다.
4. Scope 패널에서 Local·Closure·Global 영역을 확인한다.
5. 실행 전에 적은 예상과 실제 결과가 다르면 원인을 한 문장으로 쓴다.

## 30초 설명

> 실행 컨텍스트는 JavaScript가 코드를 평가하는 동안 현재 실행 상태를 추적하기 위한 스펙상의 장치입니다. 함수가 호출되면 새 실행 컨텍스트가 스택에 쌓이고, 종료되면 빠져 이전 실행으로 돌아갑니다. 식별자는 현재 렉시컬 환경에서 시작해 선언 위치에 따라 연결된 바깥 환경으로 탐색합니다. 함수가 생성 당시의 외부 환경을 계속 참조하면 외부 함수 실행이 끝난 뒤에도 그 바인딩에 접근할 수 있는데, 이것이 클로저입니다.

## 완료 체크리스트

- [ ] 실행 컨텍스트를 “객체”나 “실행 순서”라고 하지 않고 설명할 수 있다.
- [ ] `전역 → outer → inner` 호출의 push/pop 순서를 그릴 수 있다.
- [ ] 호출 위치와 선언 위치를 구분해 식별자 탐색 결과를 예측할 수 있다.
- [ ] 클로저가 값의 복사가 아니라 환경의 바인딩 참조임을 설명할 수 있다.
