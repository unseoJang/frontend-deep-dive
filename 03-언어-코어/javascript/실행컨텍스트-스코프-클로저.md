# 실행 컨텍스트 · 스코프 · 클로저

## 범위와 전제
### 포함 범위
- 대상 언어/표준: ECMAScript(ECMA-262) 기준으로 설명하며, 용어(Execution Context, Lexical Environment, Environment Record 등)는 스펙 용어를 우선 사용한다.
- 핵심 주제
  - 실행 컨텍스트(Execution Context)와 렉시컬 환경(Lexical Environment)의 역할/구성
  - 스코프(Scope)와 스코프 체인(식별자 탐색 규칙)
  - 클로저(Closure)가 "왜/어떻게" 생기고 유지되는지(함수 생성 시점, 외부 렉시컬 환경 참조)
- 런타임 범위: 브라우저/Node 공통으로 성립하는 개념을 중심으로 하되, **전역 스코프(스크립트) vs 모듈 스코프(ESM)** 같은 실행 모드 차이는 포함한다.
- 스코프 관련 필수 파생 주제(최소한)
  - `var`(함수 스코프) vs `let/const`(블록 스코프)
  - **TDZ(Temporal Dead Zone - 일시적 사각지대)**의 "관찰 가능한 결과(ReferenceError)"와 원인

### 제외 범위
- 이벤트 루프/태스크 큐/마이크로태스크 등 비동기 스케줄링 상세(별도 문서에서 다루는 게 적절)
- GC(가비지 컬렉션) 알고리즘 심화, 엔진별 최적화(개념 수준의 "참조가 남으면 환경이 유지될 수 있다"까지만)
- this 심화 규칙 전체(필요 최소만 언급: "this는 스코프 체인으로 해결되는 문제가 아니다" 정도)

### 전제 지식(최소)
- 식별자(identifier) / 변수 선언 / 함수 선언·표현식의 기본 문법
- 스코프/클로저의 직관: "내부 함수가 외부 변수에 접근 가능할 수 있다" 수준의 경험
- 에러 타입: `ReferenceError`가 "식별자 해석 실패"에서 자주 등장한다는 정도
- (선택) DevTools 기본 사용: 브레이크포인트, Call Stack / Scope 패널 확인

### 문서에서 사용하는 관찰/검증 환경(권장)
- 실행 모드: 예제는 기본적으로 "모던 JS"를 가정하며, 스크립트/모듈 차이가 중요한 예제는 명시한다(예:"ESM 기준").
- 검증 방법: 콘솔 출력 + (가능하면)DevTools Scope 패널로 "스코프 체인/클로저(Closure) 표시"를 함께 확인한다.
- TDZ 검증: `let/const/class`는 블록 시작부터 선언·초기화 지점까지 TDZ가 존재할 수 있음을 전제로 한다.

## 핵심 정의
- 실행 컨텍스트(Execution Context):
  - 정의: ECMAScript 구현이 코드를 실행(평가)하는 동안의 런타임 상태를 추적하기 위한 스펙상의 장치다. 실행 컨텍스트 스택으로 관리되며, 실행 중인 컨텍스트는 스택의 최상단(top)이다.
  - 범위/경계: "함수 호출 프레임"같은 구현 디테일을 직접 의미하지 않으며, ECMAScript 코드가 직접 관찰/접근할 수 없는 스펙 메커니즘이다.
  - 핵심 구성요소(키워드): `LexicalEnvironment`,`VariableEnvironment`,(추가 상태로 `Realm`, `ScriptOrModule` 등)

- 스코프(Scope):
  - 정의: 현재 실행 맥락에서 **값/식(특히 식별자)이 "보이고 참조 가능한 범위"**를 말한다. 스코프는 계층을 이루며, 하위 스코프는 상위 스코프를 참조할 수 있다.
  - 범위/경계: 스코프는"객체/프로퍼티 접근"규칙이 아니라 *식별자 바인딩 접근 규칙*이다(예:`obj.x`는 스코프 탐색이 아니라 프로퍼티 룩업). 스코프 자체는 개념이고, 실제 탐색은 환경 레코드/outer 연결로 모델링 된다.
  - 핵심 키워드: `lexical scope(정적 스코프)`, `scope hierarchy`,(구현 모델로)`ResolveBinding`,`[[OuterEnv]]`

- 클로저(Closure):
  - 정의: 함수 + 그 함수가 선언될 때의 주변 상태(렉시컬 환경)에 대한 참조의 결합이다. 즉, 함수가 자신의 바깥 스코프에 접근할 수 있게 한다.
  - 범위/경계:"특정 문법"이 아니라 *함수가 생성될 때 생기는 성질*이며, JS에서 클로저는 함수가 만들어질 때마다 생성된다. 또한 "값을 복사해서 저장"하는 개념이 아니라, 주변 상태(환경)에 대한 참조를 유지하는 모델로 이해하는 것이 안전하다.
  - 핵심 키워드: `outer scope`,`lexical environment`,`references to surrounding state`, `function creation time`

- 렉시컬 환경(Lexical Environment) / 환경 레코드(Environment Record):
  - 정의: (스펙 모델에서) 실행 컨텍스트의 `LexicalEnvironment`는 식별자 참조를 해석(resolve)할 때 시작점이 되는 Environment Record를 가리킨다.
	Environment Record는 식별자(Identifier) ↔ 변수/함수 바인딩의 연결을 정의하는 스펙 타입이며, 코드의 렉시컬 중첩 구조에 따라 생성되고 `[[OuterEnv]]`로 바깥 환경을 참조한다.
	- 왜 필요한가(한 줄):"이 이름(name)이 어디의 바인딩을 가리키는가?"를 현재 환경에서 시작해 `[[OuterEnv]]`로 바깥으로 확장하며 일관되게 결정하기 위해서다.

## 큰 그림: 왜 이 셋이 필요한가

### 해결해야 하는 문제(왜)
- 문제1: 식별자(name) → 값(value)을 언제/어디서 찾는가
  - JS는 실행 중에 `x` 같은 식별자 참조를 만날 때마다 "이 `x` 가 어느 바인딩을 가리키는지"를 결정해야 한다. 이때 규칙이 없으면 같은 이름이 여러 곳에 있을 때(중첩 함수/블록) 해석이 불가능해진다.
  - 스펙은 이 문제를 Environment Record와 외부 참조(outer)를 통한 탐색으로 모델링한다.

- 문제2: 선언 처리/호이스팅을 어떤 규칙으로 설명할 것인가
  - `var/let/const/function` 선언은 "코드를 한 줄씩 실행하면서" 즉석에서만 처리되는 게 아니라, **실행이 시작되기 전에 어떤 바인딩이 준비되는지**(그리고 어떤 것은 TDZ로 막히는지)가 일관된 모델로 설명돼야 한다.
  - 이때 "실행 중인 코드의 단위(전역/함수/모듈)"마다 선언 처리와 바인딩의 기준점이 필요하다.
	(이 기준점이 실행 컨텍스트/렉시컬 환경으로 이어짐)

- 문제3: 함수 실행이 끝난 뒤에도 상태가 유지되는 이유는?
  - JS에서는 내부 함수를 밖으로 반환하거나 콜백으로 넘기면, 함수 실행이 끝난 뒤에도 외부 변수에 접근 가능한 경우가 있다. 이 현상을 "우연"이 아니라 *언어가 의도한 규칙*으로 설명해야 한다(=클로저).

### 해결 구조(어떻게)
- 실행 컨텍스트(Execution Context)
  - "지금 실행 중인 코드 단위"에 필요한 런타임 상태를 묶어 관리한다. 컨텍스트는 스택(콜 스택)으로 쌓이고, 함수 진입/탈출에 따라 push/pop된다.
- 스코프/스코프 체인(Scope, Scope Chain)
  - 식별자를 해석할 때"현재 범위에서 찾고, 없으면 바깥으로 올라가며 찾는" 탐색 경로를 제공한다(개념: scope / 모델: Environment Record + outer 연결).
- 클로저(Closure)
  - 함수가 선언될 때의 렉시컬 환경(주변 상태)에 대한 참조가 유지되면, 함수가 나중에 실행되더라도 바깥 스코프에 접근할 수 있다. 이것이 "함수 + 선언 당시 렉시컬 환경" 결합으로서의 클로저다.

### 다이어그램(ASCII)
```text
(1) 실행 흐름(콜 스택)
┌───────────────┐
│ inner() EC     │  ← 현재 실행 컨텍스트
├───────────────┤
│ outer() EC     │
├───────────────┤
│ global/module  │
└───────────────┘

(2) 식별자 탐색(렉시컬 환경 체인)
inner LexicalEnv ──outer──▶ outer LexicalEnv ──outer──▶ global/module LexicalEnv ──▶ null
        │                         │                          │
   Env Record                 Env Record                  Env Record
 (bindings...)               (bindings...)                (bindings...)
 
```

## 실행 컨텍스트

### 왜(Why)
- 이 개념이 없으면 생기는 설명 불가능/디버깅 어려움:
  - 예: “지금 이 코드가 어떤 바인딩(환경)에서 실행 중인가?”를 일관되게 설명할 수 없다(전역/함수/모듈 단위의 실행 상태 추적 필요).
  - 예: “호이스팅/TDZ가 왜 발생하는가”를 ‘코드가 위로 올라간다’ 같은 비정확한 비유로만 설명하게 된다(실행 전에 어떤 환경이 준비되는지 모델이 필요).
  - 예: 디버깅에서 Call Stack(호출 스택)과 현재 실행 위치를 연결해 추적하기 어렵다(실행 모델/스택의 top이 현재 실행을 대표).

### 어떻게(How)
- "컨텍스트"가 가진 것(핵심만):
  1)`LexicalEnvironment`: 식별자 해석의 시작점이 되는 환경(환경 레코드 + outer 연결)
	2)`VariableEnvironment`: `var` 계열 바인딩을 위한 별도 환경으로 모델링되는 구성요소(스펙 구성요소로 존재)
	3)(필요 시) `this` 관련 상태: “스코프 체인”이 아니라 별도의 규칙/바인딩으로 다뤄진다(여기서는 심화 제외).
- 생성/실행 단계(개념적):
  - 생성 단계에서 생기는 것: 현재 코드 단위에 필요한 실행 상태(환경) 준비, 실행 컨텍스트 스택에 push
  - 실행 단계에서 확정되는 것: 실제 평가 진행(표현식/문 실행), 식별자 해석은 `LexicalEnvironment`에서 시작해 outer로 확장

### 예시(최소 1개)
```js
const x = "global";

function outer() {
	const x = "outer";

	function inner() {
		// 여기서 x는 어디서 찾히는가?
		console.log(x);
	}

	inner();
}

outer();
// 예상 출력: "outer"
```
---

### 검증 방법(관찰 포인트)

- 콘솔 결과로 확인:
  - `inner()` 에서의 `x` 는 전역이 아니라 `outer()` 의 바인딩이 선택된다(렉시컬 스코프 + 환경 체인 탐색).

- DevTools에서 확인(가능하면):
  - `inner()`에 브레이크포인트를 걸고 Call Stack 을 보면 `inner → outer → global/module`순서로 쌓인다.
  - Scope(또는 Closures) 영역에서 `inner`가 참조하는 상위 바인딩(예: `outer`의 `x`)이 보인다.

### 자주 하는 오해/실수(Pitfalls)

- 오해: "실행 컨텍스트 = 함수 호출 프레임(100% 동일)"
  - 실행 컨텍스트는 **스펙 모델**이고, 콜 스택/프레임은 **구현 관점**이다. 1:1로 완전히 동일하다고 전제하면 엔진/상황에 따라 설명이 흔들릴 수 있다.

- 오해: "호이스팅은 코드가 위로 이동"
  - 실제로는 실행 전에 **어떤 바인딩/환경이 준비되는지**(선언/초기화/TDZ 포함)를 모델로 설명하는 것이 정확하다.

## 스코프

### 왜(Why)
- 이 개념이 없으면 생기는 설명 불가능/디버깅 어려움:
  - 예: 같은 이름(`x`) 이 여러 블록/함수에 있을 때 "지금 참조하는 `x` 가 무엇인지"를 일관되게 설명할 수 없다.
  - 예: `var`/`let`/`const` 의 동작 차이(블록 스코프, TDZ)를"규칙"으로 설명하지 못하고 결과만 암기하게 된다.
  - 예: 특정 변수 참조가 왜 `ReferenceError`/`undefined`로 갈라지는지(초기화 전 접근 vs 존재하지 않는 식별자)를 구분하기 어렵다.

### 어떻게(How)
- 렉시컬 스코프(정적 스코프):
  - 스코프는 **코드가 작성된 위치(렉시컬 중첩)**로 결정된다. "어디서 호출했는지"가 아니라 "어디에 선언됐는지"가 기준이다.
- 스코프 체인(식별자 탐색 규칙):
  - 식별자를 해석할 때 *현재 환경에서 찾고*, 없으면 *바깥(outer) 환경으로 이동*하며 찾는다. 끝까지 없으면 `ReferenceError`다.
- `var` vs `let/const` (최소 요약):
  - `var`: 함수 스코프(블록을 무시), 선언이 해당 함수(또는 전역)의 환경에 잡힘
  - `let/const`: 블록 스코프, 선언 위치 이전 접근은 TDZ로 `ReferenceError`
- "호이스팅"을 정확히 말하기 (권장 관점):
  - 코드가 "위로 이동"하는 게 아니라, *실행 전에 바인딩이 어떻게 준비되는지*(선언/초기화/할당 타이밍)를 설명하는 용어로 쓴다.

### 예시(최소 1개)

#### 예시 1: 블록 스코프 + TDZ 관찰

```js
function demo() {
	console.log(a); // (1) ?
	// console.log(b); // (2) ?

	if (true) {
		var a = 1;
		let b = 2;
	}

	console.log(a); // (3) ?
	// console.log(b); // (4) ?
}

demo();
```
  
- 기대/관찰 포인트:
  - (1) `a`는 `undefined`로 출력될 수 있다(바인딩은 존재하지만 값이 아직 할당되지 않음).
  - (2) `b`는 TDZ로 인해 `ReferenceError`가 발생한다(초기화 전 접근).
  - (4) 블록 밖에서 `b`는 스코프 밖이므로 `ReferenceError`가 발생한다.

#### 검증 방법(관찰 포인트)
- 콘솔 결과로 확인:
  - `var a` 는 함수 스코프이므로 `if` 블록 밖에서도 접근 가능하다.
  - `let b` 는 블록 스코프이므로 블록 밖에서 접근 불가하다.
- DevTools에서 확인(가능하면):
  - `if` 블록 내부 브레이크포인트에서 Scope 패널을 보면 `b` 는 Block 스코프에, `a`는 Function/Local(또는 Script) 쪽으로 잡히는 것을 확인할 수 있다.

#### 자주 하는 오해/실수(Pitfalls)
- 오해: "스코프는 호출 위치에 의해 결정된다"
  - 스코프는 호출이 아니라 **선언 위치(렉시컬 구조)**로 결정된다(동적 스코프 아님).
- 오해: "TDZ는 `let/const`가 호이스팅되지 않기 때문에 생긴다"
  - `let/const`도 바인딩은 준비되지만, *초기화 전 접근이 금지되는 규칙 때문에 TDZ*가 관찰된다.
- 실수: `for` 루프에서 `var` 로 캡처하고 비동기에서 기대와 다른 값이 나오는 문제
  - 루프 변수의 스코프 범위를 착각하면 클로저/비동기에서 오류가 재현된다(다음 '클로저' 섹션에서 연결).

## 클로저

### 왜(Why)
- 이 개념이 없으면 생기는 설명 불가능/디버깅 어려움:
  - 예: 함수 실행이 끝났는데도 외부 변수에 접근/수정이 가능한 이유를 설명할 수 없다.
  - 예: 콜백/이벤트 핸들러/비동기 코드에서 "왜 예전 상태가 유지되거나, 왜 의도와 다른 값이 출력되는지"를 원인 단위로 추적하기 어렵다.
  - 예: "상태 은닉(캡슐화)" 패턴을 전역 변수 없이 구현하는 원리를 설명할 수 없다.

### 어떻게(How)
- 핵심 원리:
  - 함수는 선언(생성)될 때의 렉시컬 환경에 대한 참조를 가질 수 있고, 그 참조가 살아있는 동안 외부 환경(바인딩)이 유지될 수 있다.
- 클로저가 "문제"로 드러나는 전형적인 조건:
  - 내부 함수가 외부 식별자를 참조한다.
  - 그 내부 함수가 외부로 전달된다(반환/인자로 전달/이벤트 등록 등) 그리고 나중에 실행된다.
- "값을 복사"가 아니라 "환경(바인딩) 참조"라는 점:
  - 같은 바인딩을 공유하면, 나중에 실행될 때도 최신 값(또는 변경된 상태)을 보게 될 수 있다.

### 예시(최소 1개)

#### 예시 1: 상태 은닉(카운터)
```js
function createCounter(){
	let count = 0;

	return function inc() {
		count += 1;
		return count;
	};
}

const counter = createCounter();

console.log(counter()) // 1
console.log(counter()) // 2
console.log(counter()) // 3
```
- 관찰 포인트:
  - `createCounter()` 실행은 끝났지만, 반환된 `inc()`는 `count`에 계속 접근한다.
  - `count`는 전역이 아니며, 외부에서 직접 접근할 수 없다(은닉).

#### 검증 방법(관찰 포인트)
- 콘솔 결과로 확인:
  - `counter()` 호출 횟수에 따라 `count`가 누적된다(상태 유지).
- DevTools에서 확인(가능하면):
  - `inc` 내부에 브레이크 포인트를 걸고 Scope/Closure 영역에서 `count`바인딩이 유지되는지 확인한다.

#### 자주 하는 오해/실수(Pitfalls)
- 오해: "클로저는 함수 실행이 끝난 뒤에 생긴다"
  - 클로저는 함수가 생성될 때 성립하며, 실행이 끝난 뒤에 "갑자기 만들어지는 것"이 아니다.
- 오해: "클로저는 값을 복사해서 저장한다"
  - 클로저는 보통 *값이 아니라 바인딩(환경) 에 대한 참조*를 유지한다.
- 오해: "클로저 = 메모리 누수"
  - 누수는 "더 이상 필요 없는 참조가 계속 유지"될 때 발생한다. 클로저 자체는 정상 메커니즘이고, 참조를 끊으면 회수될 수 있다.
- 실수: 루프 변수(`var`)를 캡처한 비동기 콜백이 모두 같은 값을 출력하는 문제
  - 스코프(블록 스코프/함수 스코프)와 결합되면 클로저 문제가 자주 재현된다(다음 섹션에서 연결).
