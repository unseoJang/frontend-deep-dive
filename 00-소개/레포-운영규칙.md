# 레포 운영 규칙

## 목적
이 레포를 “한 번 쓰고 끝”이 아니라, **시간이 지나도 다시 꺼내 볼 수 있는 프론트엔드 딥다이브 지식베이스**로 유지한다.  
문서 추가/수정/정리/폐기의 기준을 일관되게 유지한다.

## 적용 범위
- 대상: 이 레포의 모든 문서(.md), 디렉토리 구조, 참고자료 목록
- 비대상: (선택) 임시 메모/드래프트가 있다면 별도 폴더로 분리하고 운영 범위에서 제외한다.

## 디렉토리/파일 추가 규칙
- 문서는 반드시 주제에 맞는 폴더에 위치시킨다. (예: 네트워크 → `05-네트워크/`)
- 파일명은 "주제-핵심키워드" 형태로 짓고, 동일 주제는 같은 규칙으로 맞춘다.
  - 예: `http-캐시-cache-control-etag.md`
- 새 문서를 만들 떄는 최소한 아래를 포함한다.
  - 목적 / 전체 / 본문(정의+원리) / 예시 / 요약 / 참고자료 / 마지막 업데이트

## 문서 수정 규칙(변경 기록)
- 모든 문서는 하단에 `마지막 업데이트: YYYY-MM-DD`를 유지한다.
- 큰 변경(구조 변경/정의 수정/결론 변화)은 "변경 이유"를 commit을 통해 1~3줄로 남긴다.
  - 예: "브라우저/Node 이벤트 루프 개념이 혼합되어 오해 소지가 있어 문서를 분리"

## 작업 단위 관리(개인 기준)
- 하나의 커밋은 가능하면 "하나의 문서/하나의 주제 변경"으로 제한한다.
- 변경이 커질 경우 브랜치로 분리한다.
  - 브랜치 예: `docs/event-loop`, `docs/http-cache`
- 문서 추가/수정 후에는 아래 최소 점검을 수행한다.
  - 링크 깨짐 여부
  - 목차/해당 구조
  - 코드/명령 재현 가능 여부(가능한 범위에서)

## 문서 품질 기준(최소 체크리스트)
- [ ] 목적이 1문장으로 적혀 있다.
- [ ] 핵심 정의가 명확하다(용어/범위 포함).
- [ ] “왜/어떻게” 흐름이 있다(암기용 나열 금지).
- [ ] 예시가 최소 1개 있다(코드/시나리오/다이어그램 중 택1).
- [ ] 검증 방법 또는 체크리스트가 있다(가능한 경우).
- [ ] 자주 하는 실수/오해가 있다.
- [ ] 참고자료가 있다(가능하면 공식 문서 우선).
- [ ] 마지막 업데이트가 최신이다.

## 정리/리펙토링/폐기 규칙
- 중복 문서는 합치고, 기존 문서에는 "이동/통합 안내 링크"를 남긴다.
- 내용이 오래되어 위험하거나 사실성이 떨어질 가능성이 높으면 `DEPRECATED`를 선언한다.
  - 상단에 사유/대체 문서 링크/최종 확인 날짜를 남긴다.

## 업데이트 주기(권장)
- 도구/프레임워크/라이브러리 문서: 주기적으로 재확인(예: 3~12개월 단위)
- 표준/원리 문서: 개념 변경이 없으면 필요할 때만 보강
